# Privacy challenge: private linked point locks

The optional extension uses the point-lock alternative explicitly allowed by the project specification. The basic Keccak HTLCs remain available. `PrivateHTLC.sol` is deployed separately for MST on Ethereum Sepolia and native ETH on Arbitrum Sepolia. It uses the BN254 G1 curve and Ethereum's EIP-196 scalar-multiplication precompile. No bridge, oracle, trusted intermediary or trusted setup participates.

## Protocol and verification

Let `G = (1,2)` be the generator of a prime-order group of order `n`. All secrets are uniform nonzero scalars below `n`, generated by rejection sampling with the browser/Node cryptographic RNG.

1. Bob generates a fresh private offset `k` and sends only `D = kG` directly to Alice. Bob saves `k` in his private backup. He must use a new offset for each exchange.
2. Alice generates `a` and two independent random swap identifiers. She constructs the Arbitrum lock point `A = aG` and the Ethereum lock point `M = A + D`. She rejects the identity point. Ethereum uses the longer deadline.
3. Alice proves knowledge of `a` without revealing it. With fresh nonce `r`, she sends commitment `R = rG` and response `z = r + c*a mod n`, where `c` is the Keccak-256 Fiat-Shamir challenge reduced modulo `n`. The transcript includes a protocol domain, both chain IDs, token and escrow addresses, both participants, amounts, deadlines, swap IDs, lock points, offset point and `R`, encoded with fixed-width ABI fields.
4. Alice locks MST to `M`. Bob checks `D = kG`, `M = A + D`, and the Schnorr equation `zG = R + cA`. He independently verifies the configured Ethereum escrow, its MST token binding, the confirmed creation receipt and all recorded lock terms. The second lock function repeats these checks before broadcasting ETH. An invalid proof, changed agreement, unrelated point pair or wrong offset prevents Bob from committing ETH.
5. Bob locks ETH to `A`. Alice verifies both active locks and their receipts before claiming ETH with `a`. The Arbitrum contract checks `aG = A`, pays only Alice and emits `a`.
6. Bob reads the confirmed Arbitrum claim and calculates `b = a + k mod n`. He verifies `bG = M` and claims MST with `b`. The Ethereum contract pays only Bob. Since `k` is nonzero and the identity lock is forbidden, `a` and `b` are nonzero and different.
7. If neither participant claims, each sender refunds after its own chain's deadline. If no counter-lock occurs, Alice can refund MST. Claims require inclusion strictly before expiry; refunds require time at or after expiry. Each contract acts independently.

The relation proof stays off chain. On-chain creation records contain only one leg's identifier, participants, amount, point and deadline. They do not contain `D`, `R`, `z`, the peer identifier or a common transcript digest. Publishing the handoff transcript would reveal the intended link, so the interface labels it **Peer handoff (never publish)**. It contains no private scalars but still needs a private transport channel between the participants.

## Why neither party can take both assets

Before Alice's first claim, Bob knows `k` but does not know `a` or `b`. Recovering either from its point requires solving a discrete logarithm. Alice knows `a` and `D`, but cannot compute `k` or `b` from them. The proof prevents Alice from choosing a known `b` and an unrelated or unknown first secret: she must demonstrate knowledge of the scalar of `A`, and Bob checks the algebraic relation using his own `k` before locking ETH.

After `a` appears, Bob can derive `b` using his private offset. An observer seeing `a` and the two points still lacks `k`. The receiver check also prevents an observer who sees a claim value in the mempool from directing the escrow to another account. As with basic HTLCs, Bob must remain online and have enough time and gas to finish before the longer deadline. Arbitrary network delays can defeat this timing assumption.

This is a Schnorr proof in the random-oracle model under the discrete-log assumption, not a SNARK. BN254 G1 has prime order and cofactor one; the Solidity lock validates canonical coordinates and the curve equation, rejects infinity, and the claim validates `0 < scalar < n`. The EVM and `@noble/curves@1.9.0` points are cross-checked by actual contract claims. The implementation does not use pairing operations. No independent cryptographic audit is claimed.

## What remains visible

| Observer sees | Privacy consequence |
| --- | --- |
| Different points, swap IDs and scalar claim values | No shared unlocking value directly pairs the legs. The observer cannot derive the second claim from the first without the private offset. |
| The same Alice/Bob account addresses, contract addresses, amounts and nearby block times | Strong metadata correlation remains possible. This construction does not provide transaction anonymity or defeat a motivated timing/account analysis. |
| Both scalar values after both claims | The observer can calculate a candidate difference for any candidate pair. Without the privately exchanged offset point, that alone does not distinguish the intended pair. After the second claim, neither asset remains available. |
| A leaked offset or peer transcript | A leaked offset allows early derivation after the first claim; a leaked transcript identifies the link. Reusing `k` is unsafe because any completed pair reveals `b-a = k`, exposing later swaps using that offset. |
| The grading evidence in this repository | The evidence deliberately pairs both legs for assessment, so these demonstrated instances are publicly linked by the published evidence. The protocol itself does not publish their relation transcript on chain. |

Private backups contain spend-related protocol material. Keep them and `deployments/private-swaps/` out of version control. Never publish `offset`, `aliceSecret`, the offset point or the proof as public evidence. The CLI intentionally controls both test accounts for reproducibility; this local rehearsal process knows both secrets. The browser supports separate participants and direct peer handoff. The protocol has no trusted service holding their secrets.

## Operation and evidence

```bash
npm run test:privacy
npm run deploy:private
npm run protocol:private -- success
npm run protocol:private -- recovery
npm run check:privacy
npm run check:privacy -- --live
```

`src/private-config.json` identifies the extension's escrows. Deployment resumes recorded broadcasts and verifies creation bytecode and asset binding. Local signing uses the existing ignored `.env` role keys. CLI swaps record pending hashes before waiting and save participant material privately. Inspect a saved swap before retrying a write:

```bash
npm run protocol:private -- inspect MST_SWAP_ID
npm run protocol:private -- claim MST_SWAP_ID ethereum
npm run protocol:private -- refund MST_SWAP_ID arbitrum
npm run protocol:private -- refund MST_SWAP_ID ethereum
```

In the browser, Bob generates and saves his offset before sharing its point. Alice enters that point, prepares the plan and saves her participant backup. After locking MST, she sends the peer plan directly to Bob. Bob imports it while retaining his matching offset, verifies the proof and MST receipt, locks ETH and returns the updated peer plan. Alice imports that update, preserving her secret, and claims ETH. Bob supplies the confirmed ETH claim hash to derive and claim MST. In one browser, switching MetaMask accounts preserves the current exchange; each participant still needs a backup before reload. Status and refunds refresh independently per chain.

To create another plan, save the current participant backup and choose **Start new private session**. This clears its local secret material and requires Bob to generate a fresh offset. Existing backups can restore an unfinished exchange. Never import a previously used offset for a new exchange.

The local tests cover the positive two-chain flow, distinct on-chain values, changed terms/proofs, unrelated points, wrong private offset, incorrect claim values, no transaction broadcast on failed verification, receiver authorization, both timeout paths, curve/scalar boundaries, failed transfers and reentry. `private-success.json` and `private-recovery.json` record actual testnet receipts and final states. `private-verification.json` is the independent read-only check of those transactions, creation bytecode and distinct claim values. The failed verification cases run before the real counter-lock and verify Bob's nonce did not advance; no failed on-chain transaction is claimed.
